The Hiretrack admin dashboard gives authorised staff complete operational visibility and control over the platform. From a single API surface you can manage every candidate, inspect every mock interview session, tune the AI prompts that power Groq (Llama 3.3) responses, configure subscription plans and process refunds, control the Adzuna job scraper, and adjust global system settings — all without touching application source code.

## Admin authentication

Admin authentication is **completely separate** from the candidate authentication flow. Admin tokens are validated against the `admin` and `super_admin` roles independently; a candidate JWT is rejected outright at the admin login endpoint.

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/api/admin/auth/login` | Authenticate with admin email and password — returns `accessToken` and `refreshToken` |
| `POST` | `/api/admin/auth/logout` | Invalidate the admin session (client discards the token) |
| `POST` | `/api/admin/auth/refresh` | Exchange a refresh token for a new access token |
| `GET` | `/api/admin/auth/me` | Retrieve the current admin profile and permission list |

### Seeding the first admin

Before any admin can log in, the initial `super_admin` account must be created by running the seed script once against your MongoDB instance:

```bash
node backend/src/scripts/seedAdmin.js
```

The script connects to the URI in your `.env`, checks whether the admin account already exists, and either creates or resets it. On success it prints the login credentials to stdout.

<Warning>
`seedAdmin.js` contains a hardcoded password (`passwore123`) and a hardcoded email (`aftab@admin.com`). **Change both values before running the script in any production or staging environment.** Committing real credentials to source control is a security risk.

When run against an **existing** admin account the script resets the role to `admin` (not `super_admin`) and resets the password. The `adminAuth` middleware automatically self-heals the `aftab@admin.com` account back to `super_admin` on next login, but you should verify the role after seeding if you rely on `super_admin` privileges immediately.
</Warning>

## Admin roles and permissions

Hiretrack uses a role-based access control (RBAC) system defined in `middleware/rbac.js`. Two primary admin roles are relevant for day-to-day operations:

| Role | Description |
|------|-------------|
| `admin` | Can view and manage users, jobs, templates, prompts, payments, scraper, logs, analytics, and settings |
| `super_admin` | Wildcard (`*`) access — all `admin` permissions plus the ability to delete users and override any permission check |

Two additional roles exist for more restricted staff access:

| Role | Description |
|------|-------------|
| `content_manager` | Can manage jobs, templates, and control the scraper |
| `support` | Can view and update users, issue payment refunds, and view logs |

Fine-grained permission strings (e.g. `update:prompts`, `run:scraper`, `refund:payments`) are checked per-route via the `requirePermission()` middleware. `super_admin` bypasses all individual permission checks.


Key fields returned by `GET /api/admin/stats`:

| Field | Description |
|-------|-------------|
| `totalUsers` | Total candidate accounts (excludes admin users) |
| `premiumUsers` / `freeUsers` | Premium vs free candidate split |
| `activeUsers` | Candidates with `isActive: true` |
| `newUsersThisWeek` | New candidate registrations in the last 7 days |
| `totalInterviews` | All interview configs ever created |
| `interviewsToday` | Interviews created since midnight today |
| `jobsCount` | Active (non-archived) job listings |
| `applicationsCount` | Combined resumes + sessions (proxy for application activity) |
| `totalRevenue` | Sum of all `success`-status transactions |
| `platformAvgScore` | Mean `overallScore` across all completed sessions |
| `activities` | Up to 8 most recent platform events across registrations, sessions, and resumes |
| `charts` | 6-month trend data for user growth, revenue, and interview counts, plus current-week daily activity |
| `recentErrors` | Last 5 audit log entries with `failed` or `warning` status |

## Audit logging

Every significant admin action is captured in the `AuditLog` MongoDB collection. Log entries are categorised and carry a status so failures are immediately visible.

```http
GET /api/admin/logs?page=1&limit=12&category=auth&status=failed
```

**Query parameters**

| Parameter | Values | Description |
|-----------|--------|-------------|
| `page` | integer | Page number (default `1`) |
| `limit` | integer | Results per page (default `12`) |
| `category` | `auth` \| `admin` \| `ai` \| `payment` \| `scraper` \| `email` | Filter by log category |
| `status` | `success` \| `failed` \| `warning` \| `info` | Filter by outcome |
| `search` | string | Full-text search across `action` and `details` fields |

**Example log entry**

```json
{
  "_id": "64c...",
  "category": "ai",
  "action": "groq_completion_success",
  "status": "success",
```

## Analytics

`GET /api/admin/analytics/stats` returns platform-wide usage data including user growth, session completion rates, subscription conversion, revenue trends, and job listing activity. It accepts a `range` query parameter:

| Value | Description |
|-------|-------------|
| `7d` | Last 7 days |
| `30d` | Last 30 days (default) |
| `90d` | Last 90 days |
| `1y` | Last 12 months |

See [System Settings → Analytics](/admin/system-settings#analytics) for the full response shape.
